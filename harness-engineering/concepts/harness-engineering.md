# Harness Engineering (하네스 엔지니어링)

> AI 코딩 에이전트 시대의 새로운 소프트웨어 엔지니어링 방법론

## 한 줄 정의

**엔지니어가 직접 코드를 짜는 대신, AI 에이전트가 잘 일하도록 "환경·제약·피드백 루프"를 설계하는 엔지니어링 방식**

## 비유: 말 조련사

```
전통 개발        →  기수가 직접 달리는 것
하네스 엔지니어링 →  말(AI)에게 고삐(harness)를 씌워 방향을 잡아주는 것
                    말은 빠르지만, 고삐 없으면 엉뚱한 곳으로 간다
```

- **말** = AI 코딩 에이전트 (Claude Code, Codex 등)
- **고삐(harness)** = 스펙 문서, 린터, 테스트, 아키텍처 제약
- **조련사** = 엔지니어 (환경 설계자, 의도 명세자)

## 왜 등장했는가?

```
2024: AI가 코드를 짤 수 있다 (Copilot 시대)
2025: AI 에이전트가 독립적으로 작업한다 (Agent 시대)
2026: 에이전트를 "잘 부리는 법"이 핵심이다 (Harness 시대)
         ↑ 모델 성능보다 "하네스 품질"이 성패를 가른다
```

- OpenAI: 3명 엔지니어 + Codex 에이전트로 5개월간 100만 줄 코드 생성
- Peter Steinberger: 1인 개발, 한 달에 6,600+ 커밋
- 핵심 발견: **가장 어려운 건 모델이 아니라 환경·피드백·제어 시스템 설계**

## 핵심 3요소 (Martin Fowler 정리)

```
┌─────────────────────────────────────────────────┐
│              Harness Engineering                │
│                                                 │
│  ┌──────────────┐  ┌──────────────┐  ┌────────┐│
│  │ 1. 맥락 공학  │  │ 2. 아키텍처  │  │3.엔트로││
│  │  (Context     │  │    제약      │  │피 방지 ││
│  │  Engineering) │  │(Architecture │  │(Entropy││
│  │              │  │ Constraints) │  │ Guard) ││
│  └──────┬───────┘  └──────┬───────┘  └───┬────┘│
│         │                 │              │      │
│    에이전트에게      에이전트가 벗어    코드베이스│
│    "무엇을 알려줄    나지 못하게       가 썩지    │
│     것인가"         "울타리 치기"     않게 관리  │
└─────────────────────────────────────────────────┘
```

### 1. 맥락 공학 (Context Engineering)

에이전트에게 "무엇을 알려줄 것인가"를 설계하는 것.

| 요소 | 설명 | 예시 |
|------|------|------|
| AGENTS.md | 에이전트가 따를 규칙 문서 | 코딩 컨벤션, 금지사항 |
| VISION.md | 전략적 경계·목표 | 아키텍처 방향, 기술 스택 |
| 스펙 문서 | 작업별 상세 사양 | 요구사항 ID로 추적 가능 |
| 관찰성 데이터 | 로그, 메트릭, 트레이스 | 에이전트가 버그 재현 시 활용 |

### 2. 아키텍처 제약 (Architecture Constraints)

에이전트가 "멋대로" 하지 못하게 울타리를 치는 것.

```
Types → Config → Repo → Service → Runtime → UI
 (각 계층은 아래 방향으로만 의존 가능, 역방향 금지)
```

- 커스텀 린터: 구조적 규칙을 코드로 강제
- ArchUnit 같은 구조 테스트
- 검증 게이트: 타입체킹 → 린팅 → 테스트 → 빌드 → 보안스캔

### 3. 엔트로피 방지 (Entropy Guard / Garbage Collection)

시간이 지나면 코드가 "썩는다" — 이를 주기적으로 청소하는 에이전트.

- 문서 ↔ 코드 불일치 탐지
- 아키텍처 위반 감지
- 데드 코드 제거
- 주기적 자동 실행

## 엔지니어 역할의 변화

```
┌──────────────────┐         ┌──────────────────┐
│   Before (전통)   │         │  After (하네스)    │
├──────────────────┤         ├──────────────────┤
│ 코드 직접 작성    │   →     │ 의도/스펙 설계     │
│ 디버깅           │   →     │ 환경/제약 구성     │
│ PR 코드 리뷰     │   →     │ 프롬프트 리뷰      │
│ 알고리즘 구현    │   →     │ 검증 게이트 설계   │
│ 개별 작업 집중   │   →     │ 병렬 에이전트 관리 │
└──────────────────┘         └──────────────────┘
```

## 실전 워크플로우

```
1. 스펙 작성 ─────→ 상세 요구사항 + 검증 메타데이터 정의
       │
2. 에이전트 지시 ──→ 구조화된 프롬프트로 작업 위임
       │
3. 자동 검증 ─────→ 린트 → 타입체크 → 테스트 → 빌드 → 보안
       │              (에이전트가 스스로 이 루프를 돌림)
       │
4. 크로스 검증 ───→ 다른 AI 모델로 세컨드 오피니언
       │
5. 인간 리뷰 ────→ 아키텍처 결정, 제품 동작 이상 시에만
       │
6. 머지 & 배포
```

## Peter Steinberger의 10가지 교훈

1. **완벽주의를 내려놔라** — AI 코드가 내 취향과 다를 수 있다. 받아들여라
2. **자동 검증 루프를 만들어라** — 컴파일·린트·테스트를 에이전트가 스스로 돌리게
3. **Prompt Request 문화** — 코드 리뷰 대신 프롬프트를 리뷰
4. **아키텍처 중심 논의** — PR 토론 → 설계 결정 토론으로 전환
5. **병렬 에이전트 운영** — 5~10개 동시 운영으로 몰입 유지
6. **계획 수립에 투자하라** — 좋은 스펙 = 좋은 결과물
7. **의도적 모호성** — 때로는 덜 구체적인 프롬프트가 더 나은 해법을 발견
8. **로컬 CI 우선** — 원격 CI 10분 대기보다 로컬 테스트가 빠르다
9. **지루한 작업은 위임** — 데이터 변환 등 반복 작업은 에이전트에게
10. **결과 지향적 사고** — 알고리즘 퍼즐보다 제품 출시에 집중

## Anthropic의 장기 실행 에이전트 하네스 패턴

### 2단계 에이전트 구조

```
┌─────────────────┐     ┌─────────────────┐
│ 초기화 에이전트   │ ──→ │  코딩 에이전트    │ (반복)
│ (1회만 실행)     │     │ (매 세션 실행)   │
├─────────────────┤     ├─────────────────┤
│ init.sh 생성     │     │ 진행 파일 읽기   │
│ progress.txt     │     │ 단일 기능 작업   │
│ 기능 목록 구조화  │     │ git 커밋        │
│ git 초기화       │     │ 진행 파일 갱신   │
└─────────────────┘     └─────────────────┘
```

### 핵심 원칙
- **한 번에 하나의 기능만** — 에이전트가 너무 많이 하려는 경향 방지
- **진행 상황 파일** — 세션 간 컨텍스트 유지 (시프트 근무 인수인계)
- **테스트 중심** — Puppeteer MCP 등으로 E2E 테스트 필수
