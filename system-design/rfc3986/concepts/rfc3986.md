# RFC 3986: URI Generic Syntax

## 0. 약어부터 풀어두기

| 약어 | 풀네임 | 한 줄 설명 |
|---|---|---|
| **IETF** | Internet Engineering Task Force | 인터넷 프로토콜 표준을 만드는 비영리 표준화 기구. 1986년 발족. TCP/IP, HTTP, SMTP 등 인터넷의 거의 모든 핵심 프로토콜을 표준화함. **회원 가입 없이 누구나 참여**할 수 있는 게 특징(W3C, ISO와 다른 점). |
| **RFC** | Request for Comments | 원래는 "코멘트 요청해" 라는 의미로 1969년 ARPANET 시절부터 쓰던 메모 형식. 지금은 IETF가 발행하는 **공식 표준 문서**의 이름. 번호로만 부른다(RFC 2616 = HTTP/1.1, RFC 3986 = URI). 이름이 "요청"인데 실제로는 표준이라 헷갈리지만, 역사적 명명을 그대로 유지. |
| **URI** | Uniform Resource Identifier | "자원을 식별하는 통일된 문자열". RFC 3986이 정의. |
| **URL** | Uniform Resource Locator | URI 중에서 "어떻게 접근하는지(위치)"까지 알려주는 것. URI의 부분집합. |
| **URN** | Uniform Resource Name | URI 중에서 "이름만으로 영구 식별"하는 것. 자원이 사라져도 식별자는 유효. URI의 부분집합. |
| **ABNF** | Augmented Backus-Naur Form | 문법을 형식적으로 적는 표기법. RFC 5234에서 정의. RFC 3986의 ABNF 블록은 URI 문법의 **공식 정의**다. 본문보다 ABNF가 우선. |

> RFC 3986는 STD 66(Internet Standard 66)으로 승격된, URI 문법의 **공식 결정판**이다. 2005년 1월 출판되어 RFC 2396, RFC 2732, RFC 1808을 폐기(obsolete)했다.

## 1. 왜 URI가 필요했는가 (배경 서사)

### 문제: 자원마다 식별 방식이 따로 놀았다

웹 초창기에는 자원의 종류마다 표기법이 달랐다.
- 파일 시스템 경로: `/usr/local/bin/foo`
- FTP 주소: `ftp.example.com:/pub/file`
- 메일 주소: `bob@example.com`
- HTTP URL: `http://example.com/page`
- ISBN(책 식별자): `0451450523`
- DOI(논문 식별자): `10.1000/182`

이걸 그대로 두면 **하나의 시스템이 모든 자원을 다루려면 각 표기법을 일일이 파싱**해야 한다. 게다가 새 자원 종류가 등장할 때마다 파서를 또 만들어야 한다.

### 해결: 공통 문법 + scheme로 분기

RFC 3986의 발상은 이렇다.

> "자원의 종류는 다양해도, **식별자 문자열의 외형 문법은 통일**하자.
> 종류별 차이는 맨 앞 **`scheme:`**으로 구분하자."

그래서 모든 자원 식별자가 `scheme:나머지` 모양이 된다.

```
http:  //example.com/page
mailto:bob@example.com
urn:   isbn:0451450523
ftp:   //ftp.example.com/pub/file
file:  ///usr/local/bin/foo
data:  text/plain;base64,SGVsbG8=
```

이렇게 하면:
- **일반 파서**는 `scheme:` 만 보고 컴포넌트(scheme/authority/path/query/fragment)를 분해할 수 있다.
- **scheme별 의미**(http는 어떻게 접속하나, mailto는 어떻게 보내나)는 각 scheme의 명세서가 따로 정의한다.
- 새 자원 종류가 생기면 **scheme만 새로 등록**하면 된다.

이게 RFC 3986의 한 줄 요약이다: **"scheme을 모르는 파서도 일반 컴포넌트를 추출할 수 있는 통일 문법을 정의한다."**

### 비유: 우편 봉투

자원 식별자를 **우편 봉투**라고 생각하자.
- **scheme** = 어느 나라의 우편 시스템을 쓸지(국가 코드)
- **authority** = 우편번호 + 지역(어느 건물)
- **path** = 건물 안의 호수
- **query** = 받는 사람 메모(어떤 조건)
- **fragment** = "이 편지의 3번째 문단을 봐줘"

배달원은 봉투의 양식만 알면 어디로 보낼지 결정할 수 있다. 봉투 안의 내용물(scheme 의미)은 모르고도 봉투 자체는 다룰 수 있다.

## 2. URI vs URL vs URN — 분화 이유와 현재의 관례

### 정의 (RFC 3986 §1.1.3)

- **URI**: 자원을 식별하는 통일된 문자열 (포괄 개념)
- **URL**: URI 중에서 **위치(location) + 접근 수단**까지 알려주는 것 — "어디 있고 어떻게 가져오는지"
- **URN**: URI 중에서 **이름(name)만으로 영구 식별**하는 것 — 자원이 사라져도 식별자는 살아있음

### 관계도

```
                      URI (모든 식별자)
                     /                \
            URL (위치 알려줌)     URN (영구 이름)
            ─────────────────    ──────────────────
            http://example.com   urn:isbn:0451450523
            ftp://ftp.example    urn:uuid:...
            mailto:b@example.com urn:ietf:rfc:3986
```

### 예시 비교

| 문자열 | 분류 | 이유 |
|---|---|---|
| `http://example.com/foo` | URL (URI의 일종) | scheme이 `http` — 위치(host) + 접근(HTTP 프로토콜)을 알려줌 |
| `urn:isbn:0451450523` | URN (URI의 일종) | scheme이 `urn` — 책의 영구 이름. 책이 절판되어도 ISBN은 그대로 |
| `urn:uuid:f81d4fae-7dec-11d0-a765-00a0c91e6bf6` | URN | 어떤 인스턴스의 영구 ID. 위치 정보 없음 |
| `/foo/bar` | **상대 참조(relative reference)** — URI는 아니지만 URI **참조**(URI Reference)다 | scheme이 없음. base URI를 알아야 절대 URI가 됨 |
| `mailto:bob@example.com` | URL이라기엔 애매한 URI | mailto는 위치보다는 "수신자"를 표현. 분류 논쟁 있음. |

### "왜 셋으로 나뉘었나" — 현실의 답

원래 1990년대에 IETF에서 두 진영이 다투었다.
- **URL 진영(웹 사람들)**: "지금 당장 자원을 가져올 수 있어야 한다"
- **URN 진영(도서관·메타데이터 사람들)**: "자원이 옮겨가도 식별자는 그대로여야 한다 (지속성)"

타협으로 둘을 포괄하는 **URI** 라는 상위 개념을 만들고, URL/URN은 그 안의 의도적 부분집합으로 남겼다.

### 현재의 관례 (RFC 3986 §1.1.3 권고)

> **"URL/URN 대신 그냥 URI라고 부르라"**

이유:
- 실무에서 URL과 URN의 경계가 모호한 경우가 많다 (예: `data:` URI는 URL인가?)
- 같은 식별자가 시간이 지나면 다른 분류가 될 수도 있다(웹 서비스가 종료되면 URL도 단순 이름이 됨)
- 일반 파서는 어차피 둘을 구분할 필요가 없다

**그래서 RFC 3986의 제목도 "URI Generic Syntax"** — URL/URN을 가리지 않고 **URI 문법 전체**를 정의한다.

> ⚠️ 일상에서는 여전히 "URL"이 압도적으로 많이 쓰인다. 표준 용어는 URI지만 사람들과 대화할 때는 맥락에 따라 둘 다 쓴다고 보면 된다.

## 3. URI의 5컴포넌트 구조 (§3)

RFC 3986의 핵심 ABNF:

```abnf
URI         = scheme ":" hier-part [ "?" query ] [ "#" fragment ]

hier-part   = "//" authority path-abempty
            / path-absolute
            / path-rootless
            / path-empty

authority   = [ userinfo "@" ] host [ ":" port ]
```

### ASCII 분해도

표준 예시(`foo://user:pass@example.com:8042/over/there?name=ferret#nose`):

```
  foo  ://  user:pass  @  example.com  :  8042  /over/there  ?  name=ferret  #  nose
  └┬┘ └┬┘  └────┬───┘    └─────┬────┘    └─┬─┘  └────┬────┘    └─────┬────┘    └─┬─┘
 scheme   │   userinfo          host       port      path           query     fragment
         │   └─────────────── authority ──────────┘
         └ "//" 구분자는 authority가 있을 때만 등장
```

### 컴포넌트 5개 — 각 역할

| 컴포넌트 | 필수 | 의미 | 예 |
|---|---|---|---|
| **scheme** | ✅ 절대 URI에 필수 | "어느 분류·프로토콜인지" | `http`, `https`, `mailto`, `urn`, `file`, `data` |
| **authority** | ⚠️ 선택 (scheme에 따라) | "어느 권한 주체·서버" — userinfo@host:port | `user:pw@example.com:8080` |
| **path** | ✅ 항상 존재 (빈 문자열일 수도) | "자원 내부의 위치(계층)" | `/over/there`, `/foo/bar/`, 빈 `""` |
| **query** | 선택 | "추가 조건·필터 — 비계층" | `name=ferret&page=2` |
| **fragment** | 선택 | "자원 내부의 한 부분(2차 식별)" — **서버에 전송되지 않음** | `nose`, `section-4-2` |

### 자주 헷갈리는 포인트

1. **scheme은 항상 소문자로 정규화** (`http`, `HTTP` 둘 다 유효하지만 비교 시 소문자 권장).
2. **authority 앞의 `//`는 authority가 있을 때만** 붙는다. `mailto:bob@example.com`은 authority가 없으므로 `//` 없음.
3. **fragment(`#nose`)는 클라이언트만 보고 서버로 전송되지 않는다** — HTTP 요청에 fragment는 빠진다. 그래서 SPA의 `/#/page` 라우팅이 서버 로그에 안 남음.
4. **query와 fragment는 순서 고정**: 항상 `?query #fragment` 순서. `#fragment?query`는 invalid.
5. **path는 빈 문자열이 가능**: `http://example.com` 의 path는 `""`(빈 문자열)이지 `/`가 아니다. (단, 정규화 후 `/`로 보정되는 경우가 흔함)

### 의미 있는 예시 — 흔히 만나는 4가지

```
1) https://api.example.com:443/v1/users/42?fields=name,email#metadata
   scheme=https  authority=api.example.com:443  path=/v1/users/42
   query=fields=name,email  fragment=metadata

2) mailto:bob@example.com?subject=Hi
   scheme=mailto  authority=(없음)  path=bob@example.com
   query=subject=Hi  fragment=(없음)
   ← authority가 없어서 // 없음. path가 메일 주소.

3) urn:isbn:0451450523
   scheme=urn  authority=(없음)  path=isbn:0451450523
   ← path 안에 콜론(:)이 들어가도 OK. 첫 콜론은 scheme 구분자고, 그 뒤는 path.

4) data:text/plain;base64,SGVsbG8=
   scheme=data  authority=(없음)  path=text/plain;base64,SGVsbG8=
   ← 자원 자체를 path에 임베드. URI 안에 데이터가 통째로.
```

## 4. URI Reference — Absolute URI vs Relative Reference (§4)

여기서부터 §4.2 진입을 위한 중요한 개념.

### URI Reference란?

RFC 3986는 `<a href="...">`, `<img src="...">`, OpenAPI의 `$ref` 등 **다른 자원을 가리키는 모든 문자열**을 통칭해 **URI Reference**라고 부른다.

```abnf
URI-reference = URI / relative-ref
```

즉, URI Reference에는 두 종류가 있다.
- **URI** (=absolute URI): scheme이 있는 완전한 식별자. **단독으로 의미가 정해진다.**
- **relative-ref** (=Relative Reference): scheme이 없음. **base URI가 있어야 의미가 정해진다.**

### Absolute URI

```abnf
absolute-URI = scheme ":" hier-part [ "?" query ]
```

> ⚠️ 정확히는 RFC가 "absolute-URI"는 **fragment를 포함하지 않는다**고 정의한다. fragment 포함은 그냥 "URI"라고 부른다. 실무에서는 보통 둘을 합쳐서 "절대 URI"라고 말함.

예: `http://example.com/page`, `urn:isbn:0451450523`

### Relative Reference (§4.2)

```abnf
relative-ref  = relative-part [ "?" query ] [ "#" fragment ]

relative-part = "//" authority path-abempty
              / path-absolute
              / path-noscheme
              / path-empty
```

핵심: **scheme이 없다**. 따라서 단독으로는 어디를 가리키는지 알 수 없다. 반드시 **base URI**와 결합해 해석한다.

## 5. §4.2 Relative Reference — 깊이 파고들기

### 5.1 네 가지 path 종류와 그 존재 이유

`relative-part`가 **4개의 production**으로 갈라진 이유는, 첫 글자가 무엇이냐에 따라 의미가 달라지기 때문이다.

| production | 첫 글자 | 예 | 의미 |
|---|---|---|---|
| `"//" authority path-abempty` | `//` 로 시작 | `//cdn.example.com/img.png` | **network-path reference** — scheme만 base에서 빌리고 authority는 새로 지정 |
| `path-absolute` | `/` 로 시작 (단, `//`는 아님) | `/api/v1/users` | **absolute-path reference** — host는 base에서 빌리고, path는 root부터 새로 |
| `path-noscheme` | 알파벳/숫자/기타 (콜론 불가) | `users/42`, `../images/a.png` | **relative-path reference** — 현재 위치 기준 상대 경로 |
| `path-empty` | 빈 문자열 | `?query`, `#fragment`, `""` | 경로는 그대로 두고 query/fragment만 바꿈 |

### 5.2 path-noscheme의 콜론 제약 — 왜 별도 production인가

`path-noscheme`은 **첫 세그먼트(첫 `/` 이전)에 콜론(`:`)을 포함할 수 없다**.

```abnf
path-noscheme = segment-nz-nc *( "/" segment )
segment-nz-nc = 1*( unreserved / pct-encoded / sub-delims / "@" )
                ; non-zero-length segment without any ":"
```

#### 왜 이런 제약이 있는가

URI 파서는 문자열 맨 앞에서 **첫 콜론**을 찾으면 그 앞을 scheme으로 간주한다.

```
http://example.com   →  scheme = "http"
this:that/foo        →  scheme = "this"  ←  의도와 다를 수 있음!
```

만약 사용자가 `this:that/foo` 라는 **상대 경로**를 쓰고 싶었다면? 파서는 이를 "scheme이 `this`인 절대 URI"로 잘못 해석한다.

#### 해결: `./` 접두

이 모호성을 피하는 표준 우회는 **`./`로 시작**하는 것:

```
this:that/foo        →  scheme = "this", path = "that/foo"   (URI로 해석)
./this:that/foo      →  relative reference, path = "this:that/foo"
```

RFC 본문 §4.2:
> "A path segment that contains a colon character (e.g., 'this:that') cannot be used as the first segment of a relative-path reference, as it would be mistaken for a scheme name. Such a segment must be preceded by a dot-segment (e.g., './this:that')."

#### 후속 세그먼트는 OK

첫 세그먼트만 콜론 금지다. 두 번째 세그먼트부터는 콜론 허용:

```
foo/bar:baz          →  OK. 첫 세그먼트 "foo"에 콜론 없음.
foo:bar/baz          →  ❌ scheme "foo"로 오인됨.
./foo:bar/baz        →  OK. 첫 세그먼트가 "."로 시작하니 dot-segment.
```

### 5.3 path-abempty / path-empty가 따로 있는 이유

`path-abempty` = "absolute or empty" — **authority가 있을 때**의 path. `//` 뒤에 따라오는 path. `/`로 시작하거나 빈 문자열이다.

```
//example.com/foo    →  authority="example.com", path-abempty="/foo"
//example.com        →  authority="example.com", path-abempty=""  (빈 path)
```

authority가 없는데 path가 `//` 로 시작하면, 파서가 그걸 또 authority의 시작으로 오인한다. 그래서 authority 유무에 따라 path production을 분리해두는 것.

### 5.4 §5.4 Reference Resolution 예제 표 (이게 §4.2 학습의 핵심)

**Base URI: `http://a/b/c/d;p?q`**

#### Normal Examples (정상 케이스)

| Reference | Result | 해설 |
|---|---|---|
| `g:h` | `g:h` | 콜론으로 시작 → scheme이 있는 절대 URI로 인식. base 무시. |
| `g` | `http://a/b/c/g` | 같은 디렉토리(`/b/c/`) 안의 `g` |
| `./g` | `http://a/b/c/g` | 위와 동일. `./`는 "현재 디렉토리" 표시 |
| `g/` | `http://a/b/c/g/` | `g/` 디렉토리 |
| `/g` | `http://a/g` | **absolute-path** — host만 빌리고 path는 root부터 |
| `//g` | `http://g` | **network-path** — scheme만 빌리고 authority도 새로 |
| `?y` | `http://a/b/c/d;p?y` | path는 그대로, query만 교체. (path-empty + ?query) |
| `g?y` | `http://a/b/c/g?y` | path는 g, query는 y |
| `#s` | `http://a/b/c/d;p?q#s` | 모두 그대로, fragment만 추가 |
| `g#s` | `http://a/b/c/g#s` | path=g, fragment=s |
| `g?y#s` | `http://a/b/c/g?y#s` | 셋 다 |
| `;x` | `http://a/b/c/;x` | path segment에 `;` 파라미터 |
| `g;x` | `http://a/b/c/g;x` | |
| `(empty)` | `http://a/b/c/d;p?q` | 빈 reference = base 그대로 |
| `.` | `http://a/b/c/` | "현재 디렉토리"로 정규화 |
| `./` | `http://a/b/c/` | 동일 |
| `..` | `http://a/b/` | 한 단계 상위 디렉토리 |
| `../` | `http://a/b/` | 동일 |
| `../g` | `http://a/b/g` | 한 단계 위에서 `g` |
| `../..` | `http://a/` | 두 단계 위 |
| `../../g` | `http://a/g` | 두 단계 위에서 `g` |

#### Abnormal Examples (엣지 케이스)

| Reference | Result | 해설 |
|---|---|---|
| `../../../g` | `http://a/g` | **excess `..`는 root에서 멈춤** — `/` 이하로 못 내려감 |
| `../../../../g` | `http://a/g` | 동일. root 보호 |
| `/./g` | `http://a/g` | path 중간의 `/./`는 그냥 사라짐 |
| `/../g` | `http://a/g` | path 중간의 `/../`는 직전 세그먼트 제거하고 사라짐 (이 경우는 직전이 root뿐이라 그대로 root) |
| `g.` | `http://a/b/c/g.` | **`.`가 세그먼트 끝에 붙음** — dot-segment가 아니라 평범한 문자. 그대로 유지 |
| `.g` | `http://a/b/c/.g` | 동일. `.`이 시작에 붙어도 다음 문자가 있으면 그냥 평범한 세그먼트 |
| `g..` | `http://a/b/c/g..` | `..`가 세그먼트 뒤에 붙음. 평범한 세그먼트 |
| `..g` | `http://a/b/c/..g` | `..`가 세그먼트 앞에 붙음. 평범한 세그먼트 |

> **핵심 원리**: `.`, `..`는 **세그먼트 전체일 때만** dot-segment로 해석된다. `g.`, `.g` 같이 다른 문자가 붙어 있으면 그냥 평범한 문자다.

### 5.5 Reference Resolution 알고리즘 요약 (§5.2)

base에 reference를 적용해 target URI를 만드는 절차:

```
if reference.scheme is defined:
    # 자기 자신이 절대 URI
    target = reference  (단, path는 remove-dot-segments로 정규화)
else if reference.authority is defined:
    # network-path reference (// 시작)
    target.scheme = base.scheme
    target.authority = reference.authority
    target.path = remove-dot-segments(reference.path)
    target.query = reference.query
else if reference.path is empty:
    # path-empty: query/fragment만 영향
    target.path = base.path
    target.query = reference.query if defined else base.query
    target.authority = base.authority
    target.scheme = base.scheme
else if reference.path starts with "/":
    # absolute-path reference
    target.path = remove-dot-segments(reference.path)
    target.authority = base.authority
    target.scheme = base.scheme
    target.query = reference.query
else:
    # relative-path reference
    target.path = remove-dot-segments(merge(base.path, reference.path))
    target.authority = base.authority
    target.scheme = base.scheme
    target.query = reference.query

target.fragment = reference.fragment  # fragment는 항상 reference 것
```

**핵심 함수 2개**:
- `merge(base.path, ref.path)`: base의 마지막 `/` 이후를 잘라내고 reference path를 붙임
- `remove-dot-segments(path)`: `.`, `..`을 순회하며 정리

## 6. Percent-Encoding (§2 개요)

URI에 쓸 수 없는 문자(공백·한글·특수문자 등)는 **`%HH`** 형태로 인코딩한다. `HH`는 해당 문자의 UTF-8 바이트를 16진수로.

```
공백       →  %20
한글 "안"  →  %EC%95%88  (UTF-8 3바이트)
"+"        →  %2B
```

### 문자 분류

| 분류 | 문자 | 인코딩 정책 |
|---|---|---|
| **Unreserved** | `A-Z a-z 0-9 - . _ ~` | 인코딩 불필요. 인코딩해도 의미 동일 (정규화 시 디코딩) |
| **Reserved** | `: / ? # [ ] @ ! $ & ' ( ) * + , ; =` | URI 구조로 쓰일 때는 그대로, 데이터로 쓸 때는 인코딩 |
| **기타** | 그 외 모두 | 반드시 인코딩 |

#### "Reserved를 데이터로 쓸 때"란?

예: query string 안에 `&`을 값으로 넣고 싶을 때.

```
?name=A&B          ← 파서는 "name=A" 와 "B" 라는 두 쌍으로 해석
?name=A%26B        ← 인코딩하면 값은 "A&B"
```

## 7. 실전에서 어디서 만나는가

### 7.1 HTML `<a href="...">` — Relative Reference의 본진

```html
<base href="https://example.com/blog/">

<a href="post-42">post 42</a>          → https://example.com/blog/post-42
<a href="../about">about</a>           → https://example.com/about
<a href="/login">login</a>             → https://example.com/login
<a href="//cdn.example.com/img.png">   → https://cdn.example.com/img.png
<a href="#footer">footer</a>           → 현재 페이지의 #footer
```

브라우저는 페이지 URL을 base URI로 잡고(또는 `<base>`가 있으면 그걸로) `href`를 §5.2 알고리즘으로 해석한다.

### 7.2 OpenAPI `$ref` — JSON 문서 안의 Relative Reference

```yaml
# schemas/user.yaml
properties:
  pet:
    $ref: "../pets/dog.yaml#/components/schemas/Dog"
```

`$ref` 값이 URI Reference다. base는 현재 파일 위치. fragment(`#/...`)는 JSON Pointer.

### 7.3 HTTP 응답 헤더 `Location:` (리다이렉트)

```http
HTTP/1.1 302 Found
Location: /new-path
```

서버가 `/new-path`만 줘도 클라이언트는 원래 요청 URI를 base로 삼아 절대 URI로 변환한다. **RFC 7231이 RFC 3986의 reference resolution을 그대로 인용해 동작**한다.

### 7.4 git submodule, npm package 등

상대 경로로 의존성을 가리키는 거의 모든 시스템이 URI Reference 의미론을 사용한다.

## 8. 한 줄 핵심 정리

1. **RFC 3986는 URI 문법의 통일 규칙**이다. scheme-specific 의미는 모르고도 컴포넌트 분해가 가능해야 한다.
2. **URL/URN은 URI의 부분집합** — 위치를 알려주면 URL, 영구 이름이면 URN. 권고는 "그냥 URI라고 부르자".
3. **URI는 5컴포넌트**: scheme, authority, path, query, fragment. scheme + path만 있어도 URI는 성립.
4. **URI Reference = URI ∪ Relative Reference**. relative reference는 base URI가 있어야 의미가 정해진다.
5. **§4.2 Relative Reference의 4 production**(`//authority`, `/path`, `path-noscheme`, empty)은 첫 글자가 무엇이냐에 따른 분기다. 특히 `path-noscheme`은 **첫 세그먼트에 콜론 금지** — scheme 오인 방지.
6. **§5.4 표는 외울 가치가 있다**. 실무에서 헷갈리는 케이스의 답이 거기 있다.
7. **`.`, `..`는 세그먼트 전체일 때만 dot-segment**다. `g.`, `..g`는 평범한 문자열.
8. **`..` 과잉은 root에서 멈춘다**. `../../../../g` → `http://a/g`.
