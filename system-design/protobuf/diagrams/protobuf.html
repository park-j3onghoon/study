① 직렬화 결과 분해 — 번호 vs 이름

message User { int32 id = 1; string name = 2; } 의 User{id=42, name="Teddy"} 직렬화:

번호 (1, 2) → tag로 인코딩 ▪ 필드 값 (42, "Teddy") ▪ wire type 태그 (varint, length-delimited) 바이트에 ❌ 없는 것: ▪ 필드 이름 "id", "name" → 이름은 .proto/내 코드에서만 라벨로 쓰임. → 이름 바꿔도 호환됨, 번호 바꾸면 호환 깨짐.
필드 번호 (tag) 값 이름 (바이트엔 없음) 타입
.proto에 적힌 id, name 같은 이름은 직렬화 바이트 어디에도 들어가지 않는다. 바이트에는 번호 (tag) 와 값 만 들어간다. 이게 Protobuf 컴팩트의 핵심이자 호환성의 기반.

② v1 ↔ v2 양방향 호환 — 필드 추가

새 번호로 필드 추가는 양방향 호환. proto3의 default + wire format의 unknown-field-skip 덕에 가능. 단, 반드시 새 번호여야 한다. 기존 번호 재사용은 위험 (다음 다이어그램).

③ 번호 재사용 위험 시나리오

필드를 삭제할 때 같은 번호를 새 필드가 재사용하면 옛 데이터와 새 스키마가 충돌한다. reserved 선언으로 컴파일 시점에 사고를 막을 수 있다.

④ wire type 그룹 호환 매트릭스

같은 wire type 그룹 안에서 타입 변경은 호환. 다른 그룹으로 가면 호환 깨짐.

wire type 속한 .proto 타입 같은 그룹 안에서 변경
varint (0) int32, int64, uint32, uint64, sint32, sint64, bool, enum ✅ 호환 int32 ↔ int64, bool ↔ int32 등
fixed32 (5) fixed32, sfixed32, float ✅ 호환 fixed32 ↔ float
fixed64 (1) fixed64, sfixed64, double ✅ 호환 fixed64 ↔ double
length-delimited (2) string, bytes, embedded message, packed repeated ✅ 호환 string ↔ bytes (의미 주의)

실전 사례

✅ 안전한 변경
int32 score = 5 → int64 score = 5
둘 다 varint. v1 데이터를 v2 코드가 자연스럽게 읽음. 반대도 OK (int32 범위 안의 값일 때).
✅ 안전한 변경
string raw = 7 → bytes raw = 7
둘 다 length-delimited. UTF-8 검증 차이만 신경 쓰면 됨.
❌ 위험한 변경
int32 age = 3 → string age = 3
varint → length-delimited. wire type 다름. 옛 바이트 못 읽음.
❌ 위험한 변경
float ratio = 8 → double ratio = 8
fixed32 → fixed64. 같은 그룹처럼 보이지만 폭 다름. 호환 안 됨.
⚠ protoc는 호환성 검사 안 함. 위 변경들이 컴파일은 통과한다. 옛 데이터와의 호환 여부는 buf 같은 외부 도구로 별도 검증해야 한다.

⑤ Oneof — 라디오 다이얼 비유

정확히 하나만 설정 가능 ▪ 새 값 설정 시 기존 값 자동 클리어 ▪ WhichOneof('method') API로 현재 어느 게 설정됐는지 확인 ▪ 비유: 라디오 다이얼 — 한 번에 한 채널만 들림 ⚠ Oneof 호환성 함정 ▪ ✅ Oneof에 새 필드 추가 안전 ▪ ❌ 일반 필드 ↔ Oneof 이동 위험 ▪ ❌ Oneof 간 필드 이동 위험 → 그룹 소속이 바뀌면 의미가 달라짐
Oneof는 메시지 안에서 여러 필드 중 정확히 하나만 설정되도록 강제하는 문법. 비즈니스 규칙(결제 수단·알림 종류 등)을 스키마 수준에서 표현. 라디오 다이얼처럼 한 번에 한 채널.
