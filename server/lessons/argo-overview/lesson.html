Argo — 4총사 한눈에 보기

"Argo"는 단일 도구가 아니라 Argo Project라는 CNCF Graduated 프로젝트의 우산 이름입니다. 안에 도구가 4개 있어요. 맥락 없이 "Argo"만 들으면 어떤 걸 말하는지 모호하기 때문에, 먼저 4총사를 구분하고 가장 흔히 쓰이는 Argo CD에 초점을 맞춥니다.

Step 1. 왜 4개로 나뉘었나

각각 다른 시기에 다른 문제를 풀려고 나온 도구들입니다. 처음부터 한 덩어리로 설계된 게 아니라, 운영 경험이 쌓이며 별도 도구로 분리되었습니다.

  • Argo Workflows (2017, Intuit) — "K8s 위에서 ML/데이터 파이프라인 돌리고 싶다" 가 출발점.
  • Argo CD — Workflows 운영 경험에서 "배포 자체도 declarative + K8s-native로 하자" → 분리.
  • Argo Rollouts — K8s 기본 Deployment 리소스로는 Canary·Blue-Green이 표현 불가 → 분리.
  • Argo Events — 이벤트 기반 트리거(Webhook·Kafka·S3)는 Workflows에 묶기엔 너무 범용 → 분리.
핵심 포인트: 4개를 다 써야 하는 게 아니라, 필요한 것만 골라 쓴다. 가장 단독 사용 비율이 높은 건 Argo CD입니다.

Step 2. 4총사 비교표

도구한 줄 정의비유대체재
Argo CD Git 저장소가 K8s 클러스터 상태의 single source of truth (SoT). Git에 yaml 푸시 → 클러스터가 그 상태로 수렴 도면(Git)을 보고 건물(클러스터)을 계속 도면과 맞춰주는 감독관 Flux CD, Spinnaker
Argo Workflows K8s 위에서 도는 컨테이너 기반 워크플로우 엔진 (DAG·step 정의, 각 step = Pod) Airflow의 K8s-native 버전 Airflow, Tekton, Prefect
Argo Rollouts K8s Deployment 상위 호환. Canary · Blue-Green · 점진적 트래픽 이동 지원 Deployment는 "올 오어 낫싱", Rollouts는 "10% → 50% → 100%, 메트릭 보며 결정" Flagger
Argo Events 외부 이벤트(Webhook · Kafka · S3 등) → K8s 안의 트리거 (예: Workflows 시작) 외부에서 일어난 일이 K8s 안 워크플로우를 깨우는 초인종 Knative Eventing

Step 3. 그림으로 보기

Git → Argo CD → 클러스터 상태 동기화. Rollouts·Workflows는 클러스터 안 리소스, Events는 외부 이벤트의 진입 게이트.

Step 4. 가장 흔한 시나리오 — Argo CD (GitOps)

GitOps = "Git이 단일 진실의 원천(SoT)이고, 실제 시스템 상태는 Git에 맞춰 자동으로 수렴한다"는 운영 방식입니다.

  1. 개발자가 deployment.yaml 의 image tag를 v1.2.3 으로 바꿔 Git에 push
  2. Argo CD가 Git을 polling (또는 webhook으로 감지)
  3. 현재 클러스터 상태 ≠ Git 상태 → OutOfSync 감지
  4. auto-sync 설정이면 자동으로, 아니면 사람이 "Sync" 버튼 → 클러스터에 apply
  5. 이후에도 누가 kubectl edit로 클러스터를 직접 바꾸면 Argo CD가 다시 Git 상태로 되돌림 (self-heal)

왜 "그냥 kubectl apply"가 아니라 Argo CD인가?

관점kubectl apply (CI에서 직접)Argo CD (Pull 방식)
권한CI가 클러스터 자격증명 보유 (외부에 클러스터 노출)클러스터 내부 Argo CD가 Git을 pull (자격증명이 클러스터 밖으로 안 나감)
드리프트누가 손으로 바꿔도 모름Git과 다르면 즉시 감지·복구
롤백이전 CI 잡 다시 돌려야 함Git revert 하나로 끝
감사(audit)CI 로그 뒤져야 함Git 커밋 히스토리 = 변경 이력

Step 5. 흔한 오해

  • 오해 "Argo = CI/CD" → ❌. Argo CD는 CD만입니다. CI(빌드·테스트)는 GitHub Actions, Jenkins 같은 별도 도구가 담당. (Argo Workflows를 CI 용도로 쓸 수는 있지만 일반적이지 않음.)
  • 오해 "Argo Workflows = Argo CD의 일부" → ❌. 완전히 별개 도구. 같이 안 써도 됨.
  • 오해 "Argo Rollouts는 Argo CD가 있어야 동작" → ❌. 단독으로도 됨. 다만 GitOps와 같이 쓰면 시너지가 큼.
  • 오해 "K8s를 안 쓰면 Argo도 쓸 수 있다" → ❌. 4개 모두 K8s 전제. K8s 위에서만 동작합니다.

Step 6. 한 줄 정리

Argo는 K8s 위에서 "선언적(declarative) 운영"을 밀어붙이는 4개 도구의 묶음.
- CD는 상태 동기화
- Workflows는 작업 실행
- Rollouts는 점진적 배포
- Events는 외부 트리거
각각이 푸는 문제가 달라서 분리되어 있고, 필요한 것만 골라 씁니다.

Q5. 왜 Argo Project는 한 도구로 합치지 않고 CD / Workflows / Rollouts / Events 4개로 나뉘어 있는지 본인 말로 1~2문장으로 설명해보세요.
